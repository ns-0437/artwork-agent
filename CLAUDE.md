# Artwork Exception Resolution Agent

Independent six-day portfolio prototype built for a specific AI Agent Engineer application (stack: Go, TypeScript, GraphQL, Postgres, GCP). Not affiliated with, and has no access to, any real company's production systems.

**Deliverable:** resolve an artwork blocker on a simulated sticker order — inspect the file, clarify customer intent if needed, perform one eligible repair (uniform-background bleed extension), verify it, and prepare a proof — with the case persisted so work resumes after replies or failures.

Spec of record: `docs/build-brief.pdf` (the six-day build brief). When this file and the brief disagree, the brief wins; update this file to match.

## Points to remember

1. **Rules are deterministic; the model never computes or overrides a measurement.** PPI, color-mode/profile, and bleed-coverage math live in `services/image-python`, are unit-tested, and are versioned (`rule_version`). The agent (Go + LLM adapter) only chooses among `ask_clarification` / `request_repair` / `escalate` based on the rules' output — it cannot recalculate or second-guess a check result.
2. **REPAIRED is only set after exact *decoded-pixel* equality verification of the ACTUAL SAVED OUTPUT** (`services/image-python/app/repair/verify.py:verify_repair`, called from `/repair`) — decode both images and compare pixel arrays via `ImageChops.difference(...).getbbox() is None`, never compare raw file bytes or hashes. `/repair` encodes the canvas to PNG bytes FIRST, then reopens THAT PNG (`Image.open(io.BytesIO(...))`) and verifies against the reopened copy, not the in-memory canvas object still held before saving - an encode/decode artifact that only shows up after the save/reload round trip must not slip past a check that only ever looked at memory. A lossless re-encode can differ byte-for-byte while being pixel-identical, and that must still pass (see `test_a_lossless_reencode_still_verifies_pixel_identical`). `source_hash`/`derived_hash` are for the audit trail and idempotency lookups only — they are not the equality proof. If verification somehow fails, `/repair` returns `repaired: false` and discards the candidate entirely - it is never written to storage.
3. **Status ceiling, precisely:** `production_status` stays `NOT_RELEASED` always — nothing in v1 changes it. `proof_status` starts `NOT_PREPARED` and moves to `AWAITING_CUSTOMER_APPROVAL` only once a "prepare proof" step actually creates and stores a proof artifact — that transition is a system action, not a customer clicking "approve," but it must correspond to a real stored artifact, not just a status flip. `artwork_status=RESOLVED` on its own does NOT imply a proof was prepared (see brief: "'Resolved' means only the supported artwork blocker is cleared. Customer proof approval and production release are separate, unperformed steps.") - `decideArtworkStatus` (`internal/worker`) always returns `proof_status=NOT_PREPARED`, even when every check passes. **Still true after Day 4's agent loop landed**: the loop only implements step 3 (clarify/repair/escalate) of the brief's five-step loop - step 5 ("prepare a proof") is NOT implemented; `proof_status` still never leaves `NOT_PREPARED` anywhere in the current code. Never implement anything that sets proof/production status *beyond* `AWAITING_CUSTOMER_APPROVAL` / `NOT_RELEASED`.
4. **Python owns only image inspection/repair; Go owns workflow, validation, and state.** Don't let business logic (state transitions, eligibility gating on order fields, retries) creep into `services/image-python` — it should be a pure function of image bytes + declared trim/intent in, structured findings/repair result out.
5. **Every mutation needs an idempotency key + expected `case_version` check** to prevent duplicate repairs or state corruption on retry. `requestRepair`, `answerClarification`, and any agent-triggered mutation must validate both before writing.
6. **Bounded agent loop (implemented Day 4):** `worker.runAgentDecision` caps at `maxAgentToolCalls=5` decision calls and `maxAgentTransientRetries=2` retries, tracked on `orders.agent_tool_calls_used`/`agent_retries_used` (migration `0005_agent_loop.sql`) so the budget survives across replies rather than resetting each time the worker process restarts. Once the cap is hit, the loop refuses to call the provider AT ALL and escalates straight to `NEEDS_REVIEW` (`EscalateToNeedsReview`) - verified live by pre-setting the counter to 5 and confirming zero new `tool_events` rows. The budget resets only on a genuinely new artwork upload (`RecordArtworkUpload`), never on a clarification reply. A transient failure (e.g. the model not calling the required tool) retries automatically within the same invocation - observed live via Groq's occasional "tool choice is required, but model did not call a tool" error.
7. **No claim of company savings, private integration, or Sticker Mule pipeline access** anywhere in code, README, comments, or docs. This is an independent prototype based on public requirements only.
8. **`artwork_status` transitions:** BLOCKED → AWAITING_CLARIFICATION → BLOCKED (after reply) → RESOLVED (after all supported blockers verified clear); unsafe/unsupported cases go to NEEDS_REVIEW instead. A new upload (`RecordArtworkUpload`) reopens the case atomically: bumps `artwork_version`/`case_version`, resets `artwork_status` to BLOCKED and `proof_status` to NOT_PREPARED, and clears trim confirmation - a stale RESOLVED from before the new upload must never persist against artwork the system hasn't inspected. **Short-circuit to RESOLVED**: if the first inspection already finds every *expected* check PASS/WARNING-only (nothing NEEDS_INPUT, no repair required), the case completes straight through to RESOLVED on that same pass (proof_status stays NOT_PREPARED - see point 3) — don't force a clean case through a clarification or repair round it doesn't need. **WARNING is never blocking** — an RGB color-mode advisory (or any other WARNING-level finding) must not by itself prevent RESOLVED; only NEEDS_INPUT/NEEDS_REVIEW findings, or an unverified required repair, block resolution.
9. **Result vocabulary per check is exactly:** PASS / WARNING / NEEDS_INPUT / NEEDS_REVIEW. `REPAIRED` is a repair-only status, set post-verification. Don't invent alternate strings — evals and the UI key off these exact values.
10. **CMYK inputs are inspect-only in v1** — `app/repair/eligibility.py:check_eligibility` explicitly rejects `image.mode == "CMYK"` with a specific reason before anything else runs. Never `.convert("RGB")` a CMYK image to make it eligible - that reinterprets the channel values as something they're not, corrupting the color rather than repairing it. Repair otherwise preserves the source's actual mode (`"RGB"` or `"L"`, with opaque `RGBA`/`LA` reduced to one of those) end to end - the canvas, the fill color, and the pasted original are all built in that same mode, and the source's `icc_profile` (if present) is passed through on save so an RGB color profile survives the repair.
11. **Repair eligibility is a conservative demo rule, not a manufacturing-suitability proof.** Reject gradients, transparency, textured edges, and foreground objects touching the boundary — don't loosen this to get more fixtures to pass.
12. **Bleed check requires full-bleed intent AND a confirmed trim rectangle.** If either is missing, return NEEDS_INPUT — never infer trim placement by guessing from edge pixels. **Trim confirmation (v1) is explicit, not assumed:** `orders.artwork_is_trim_only` (nullable boolean, set via the `confirmTrim` mutation) records whether the customer confirms the current upload contains ONLY the trim content, no bleed margin. `app/checks/trim.py`'s `resolve_trim` is the single source of truth for what counts as a known trim rectangle: border intent needs no confirmation (the whole image is unambiguously the trim - no separate bleed region exists to be confused with); full-bleed intent needs `artwork_is_trim_only=true` (trim = whole image) or explicit trim dimensions (post-repair); anything else returns "unconfirmed" and BOTH resolution and bleed report NEEDS_INPUT rather than guessing. **PPI and bleed margin are always computed from the confirmed trim region, never from the whole canvas** — this matters once Day 3's repair can produce a canvas larger than its trim: `resolution.check_resolution` takes `trim_width_px`/`trim_height_px` explicitly (never "image" dimensions), and `bleed.check_bleed` measures the actual margin between the confirmed trim and the full canvas using that same trim-derived `effective_ppi`, not a fresh PPI computed from the larger canvas.
13. **Out of scope, don't add:** Stores/Notify/Reply/Ship integration, SVG/PDF parsing, generative upscaling, automatic color conversion, print certification, payments, production release, factory integration, multi-agent fleet, arbitrary cut contours.
14. **Provider adapter is single and replaceable** (`internal/agent.Provider`, one method `Decide`). **Actually running on Groq, not Claude, as of Day 4** - `internal/agent/groq_adapter.go`. This is a deliberate, honestly-documented substitution: the Anthropic account available for this build had no usable credits, so Groq (a fast inference host for open-weight models) was wired in as a practical stand-in. **Groq is NOT xAI's Grok** - the brief's "Grok" refers to xAI's model for the optional Day 5 comparison; Groq is an unrelated inference company. Never conflate the two in code, commits, or the case study - say "Groq" when that's what ran, and never claim "Claude" or "Grok" ran anything they didn't. Swapping to Claude (or anything else) later means writing one more `Provider` implementation; nothing else changes. A Grok (xAI) comparison remains optional Day-5 scope, gated on core evaluation gates already passing — never let it displace reliability work.
15. **Untrusted input handling:** treat all customer text/files as untrusted — enforce file signature checks, 10MB upload cap, 25-megapixel decoded limit, sandboxed decoding, and timeouts in `services/image-python`'s entry points.
16. **One execution path, built real from Day 1.** `startResolution` → enqueue job (QUEUED) → Go worker claims it → calls the Python inspect endpoint → persists findings → updates status is the single pipeline used from Day 1 through Day 4. Day 1 doesn't build a throwaway stub that gets rebuilt on Day 2 — Day 2 just makes the Python side return real checks instead of a minimal decode. Never fork a second "real" path later.
17. **Storage is behind one interface.** `internal/storage` in `services/api-go` has a `LocalDisk` implementation for dev (content-addressed by hash under e.g. `./data/artifacts`) and a `GCS` implementation added at Day 5 deploy time. Call sites never change between the two.
18. **Job claims are one atomic SQL statement**, not read-then-write: `UPDATE jobs SET status='RUNNING', worker_id=$1, lease_expires_at=... WHERE id=$2 AND status='QUEUED' AND (lease expired or unheld) RETURNING *`. Only the worker holding a live lease may progress or complete the job; a reaper reclaims expired leases.
19. **Repair identity is a DB unique constraint** (`UNIQUE(order_id, idempotency_key)` on `repairs`), not just an app-level check — a retried request finds the existing row atomically instead of racing an insert.
20. **`case_version` is checked at write time, in the UPDATE's WHERE clause**, not just read-then-compare — zero rows affected means stale, and the caller gets a version-conflict error rather than a silent overwrite. This applies equally to a **worker's own** state advance, not just client mutations: a worker that lost its lease (reclaimed by another worker) or whose job was bound to a case_version the order has since moved past must not be able to write the order forward. See point 23.
21. **Crash-safety is a tested scenario, not an assumption - but the actual kill-the-process chaos test is still NOT DONE.** The design should already make it safe (content-addressed storage keys make a retried artifact write a no-op; `CompleteRepair`/`CompleteInspection` are single transactions gated on lease + case_version, so a crash before commit just looks like a lease that will expire and get reclaimed), but nobody has literally killed a worker mid-write and confirmed it. Do this before claiming it in the case study - "the design should be safe" and "verified safe" are different claims.
22. **Fixtures and the dev/held-out split start Day 1-2, not Day 5.** A small seed set lands with the Day 1 skeleton so the real execution path has something to run against immediately; it grows through Day 2 as checks land. Day 5 is reserved for running the eval harness against the already-built set, freezing results, and deployment — not for building fixtures from scratch.
23. **A job is bound to a specific asset and case_version at creation time** (`jobs.input_asset_id`, `jobs.input_case_version`), never resolved as "whatever is latest" when the worker happens to run — a later upload must not change what an in-flight job acts on. `startResolution` (and later `requestRepair`) freeze these at enqueue time; the worker reads `job.InputAssetID`, never a fresh `LatestAssetByKind` lookup.
24. **A composite write (result + job completion + order-state advance) is ONE transaction, never two or three separate store calls.** Two separate `pool.Exec` calls cannot share a transaction, so a crash between them can leave a result stored with no completed job, or a completed job with no stored result. `store.CompleteInspection` is the pattern: begin a tx, write the asset/job/order updates inline gated the same way (lease + case_version), commit or roll back all of it together. A `SUCCEEDED` status must never be reachable without its result actually being persisted.
25. **Enqueue mutations are idempotent by construction, not by a client-supplied key.** At most one QUEUED/RUNNING job of a given type may exist per order (a partial unique index on `jobs(order_id, job_type) WHERE status IN ('QUEUED','RUNNING')`) — a repeated `startResolution` or `requestRepair` call while one is already in flight returns the existing job instead of enqueueing a duplicate. `requestRepair` ALSO carries its own client-supplied idempotency key (`jobs.idempotency_key`, distinct from the in-flight guard) per point 19. **Idempotency is checked BEFORE case_version freshness, never after** (`internal/graph/repair_idempotency.go:decideRepairRequestAction`, unit-tested without a DB): a completed repair's key match wins outright, even if the order's `case_version` has since moved past what the caller supplied - which it usually HAS, as a direct result of that same repair completing. Checking `case_version` first would make every post-completion retry fail as "stale" even though it's an exact replay of a request that already succeeded. If a key is reused with a *different* `case_version` than it was originally submitted with, that's rejected explicitly as reuse-with-different-inputs, not silently served the old result or silently accepted as new. **v1 simplification:** only one repair attempt may be in flight per order regardless of idempotency key - a `requestRepair` call with a *different* key while a different one is active is rejected (not silently redirected to the in-flight job); wait for it to finish before retrying with a new key.
26. **Dev ports are bound to `127.0.0.1`, not `0.0.0.0`**, in `infra/docker-compose.yml` (`"127.0.0.1:PORT:PORT"`) — there is no authentication or ownership check on these endpoints yet, so exposing them to the LAN would let any other device on the network hit them. Don't drop the `127.0.0.1:` prefix when adding a new port mapping.
27. **Python validates format and declared size before the expensive decode.** `Image.open()` only reads the header; check `image.format` against an explicit allowlist (PNG/JPEG) and `width*height` against the 25-megapixel cap using `image.size` *before* calling `image.load()`, which is what actually decodes pixel data. Deciding after `.load()` means an oversized or disallowed file was already fully decoded into memory before being rejected.
28. **`decideArtworkStatus` (in `internal/worker`) keeps a NEEDS_INPUT case at `BLOCKED`, not `AWAITING_CLARIFICATION` - this function itself never changed.** The transition TO `AWAITING_CLARIFICATION` is a separate, later step: `worker.runAgentDecision` runs AFTER `decideArtworkStatus`'s result has already committed, reads that committed BLOCKED/NEEDS_REVIEW state as input, and only THEN may move the case to `AWAITING_CLARIFICATION` (via `CreateClarificationAndAwait`) if it decides `ask_clarification`. The deterministic rules and the agent's action are still two clearly separate steps, never blended into one function.
29. **`decideArtworkStatus` validates completeness before it validates severity.** It first checks that every check *expected for this intent* (`expectedChecksForIntent`) is present exactly once with a result from the recognized vocabulary (point 9) - only then does it look at whether any of those results block. An empty, partial, or malformed findings list (a bug, a Python-side exception swallowed somewhere, a check that silently didn't run) must NEVER resolve a case just because it contains no NEEDS_REVIEW/NEEDS_INPUT to trip on - "nothing to block on" is not "everything passed". Incomplete/malformed results escalate to NEEDS_REVIEW, same severity as an unsafe finding, since it's a system anomaly for a human to look at, not something the customer can act on. See `internal/worker/worker_test.go` for the exact cases this covers.
30. **A new upload is a transaction, not a plain insert** (`store.RecordArtworkUpload`, used by `internal/upload`'s handler - never call `store.CreateAsset` directly for a customer's original-artwork upload). It bumps `artwork_version`/`case_version`, resets `artwork_status`/`proof_status`, and clears trim confirmation/coordinates atomically with the asset insert. Any job already in flight against the old `case_version` is automatically voided by the same guard in `CompleteInspection` - no separate cancellation needed.
31. **Repair only ever runs against a confirmed trim-only upload** (`intent='full_bleed' AND artwork_is_trim_only=true`) - checked in `worker.runRepair` BEFORE calling Python at all, not left to the endpoint to assume. `/repair` itself never resolves trim ambiguity; it treats the whole input image as the trim, which is only a safe assumption because Go already verified the precondition. A repair requested without it is recorded as a REJECTED `repairs` row with that reason - the original is never touched, and `artwork_status` becomes NEEDS_REVIEW.
32. **`store.CompleteRepair` is the same pattern as `CompleteInspection`, extended**: one transaction commits the job's SUCCEEDED status, the `repairs` row (REPAIRED or REJECTED, `ON CONFLICT (order_id, idempotency_key) DO NOTHING` so a duplicate completion is a safe no-op), and - only when repaired - the new `repaired`/`preview` assets, the order's now-known `trim_x_px`/`trim_y_px`/`trim_width_px`/`trim_height_px`, fresh findings from the post-repair recheck, and the state advance. An ineligible/unverified repair still commits (the REJECTED row + NEEDS_REVIEW) but touches nothing else - no assets, no trim coordinates, original completely untouched. New asset bytes are written to `internal/storage` BEFORE the transaction begins (storage writes aren't transactional with Postgres); content-addressing makes a retried write of the same bytes a safe no-op if the transaction that would have recorded it never committed.
33. **The post-repair recheck passes `trim_width_px`/`trim_height_px` explicitly to `/inspect`** (`pyclient.InspectInput.TrimWidthPx/TrimHeightPx`, populated from the `/repair` response) - it does NOT rely on `artwork_is_trim_only` for this second call, since the new canvas is no longer trim-only (it now has real bleed margin). `trim.py:resolve_trim` checks explicit trim dimensions first, before intent/confirmation, specifically for this case.
34. **The preview (trim/bleed overlays) is a separate asset from the repaired file**, both written by `worker.runRepair`/`store.CompleteRepair` (`kind='repaired'` vs `kind='preview'`). `app/repair/preview.py:render_preview` draws on a *copy* of the canvas - overlays never touch the actual repaired file that gets used for anything downstream.
35. **`orders.current_asset_id` is the single source of truth for "the artwork right now"** - never `LatestAssetByKind(orderID, "original")` for inspection or (future) proof generation, only for finding the pristine source to REPAIR. It's set by `RecordArtworkUpload` (to the new upload) and by `CompleteRepair` on success (to the new repaired asset), atomically with everything else those transactions do. `resolveStartResolution` reads it via `GetAsset(*order.CurrentAssetID)`. Getting this wrong (falling back to "latest original") is exactly how a re-inspection after a successful repair can silently reintroduce a blocker the repair just cleared - it was a real bug here once, don't reintroduce it.
36. **A job's own recheck must pass the order's known trim dimensions, not just the repair's own recheck.** `worker.runInspect` passes `order.TrimWidthPx`/`TrimHeightPx` to `/inspect` explicitly whenever `job.InputAssetID == order.CurrentAssetID` and those trim fields are set (i.e. re-inspecting an already-repaired canvas) - exactly the same thing `runRepair`'s own post-repair recheck does (point 33). Without this, `resolve_trim` would fall back to treating the WHOLE canvas as the trim (since `artwork_is_trim_only` is never reset after a successful repair), measuring zero bleed margin and reintroducing the missing-bleed finding. Only apply this when the job's asset actually matches the order's current one - a job bound to a stale (pre-repair) asset must not borrow trim coordinates that describe a different one.
37. **Declared physical dimensions must be positive** - enforced at the schema level (`orders` has `CHECK (declared_width > 0)` / `CHECK (declared_height > 0)`, migration `0004_current_asset_and_validation.sql`) and defensively again in `services/image-python` (`app/repair/geometry.py:validate_declared_size`, called from both `/inspect` and `/repair`) for any caller that bypasses the DB. A zero or negative declared size divides by zero or produces nonsense PPI in `resolution.py`/`bleed.py`.
38. **A single min-axis `effective_ppi` can falsely satisfy bleed when the artwork's pixel aspect ratio doesn't match the declared physical aspect ratio** - one axis ends up measured against the wrong axis's PPI. Computing genuinely correct per-axis PPI is a bigger change than v1 scope; instead `/repair` rejects the mismatch outright (`geometry.py:validate_aspect_ratio`, 2% relative tolerance for pixel rounding) rather than silently treating the artwork as if it were stretched to fit. This check lives in the repair path specifically, since that's where a false pass would actually produce a wrongly-sized canvas - `resolution.check_resolution`'s own min-axis formula is unchanged and matches the brief's spec exactly.
39. **The expanded canvas size is capped BEFORE `Image.new()` ever runs** (`extend_background.py`, `MAX_CANVAS_PIXELS = 25_000_000`, raises `CanvasTooLargeError` which `/repair` turns into a normal `repaired: false` response) - an abnormally large `effective_ppi` (e.g. from a tiny declared physical size) must not be allowed to drive a memory-exhausting allocation.
40. **The agent's decision is a suggestion Go's deterministic guards can safely ignore if wrong.** `worker.triggerAutoRepair` (the `request_repair` action's handler) just enqueues a job the same way `requestRepair` does - `worker.runRepair`'s own precondition check (point 31: `intent=full_bleed AND artwork_is_trim_only=true`) is the actual safety net. If the model ever chooses `request_repair` when that precondition doesn't hold, the job is simply REJECTED with a clear reason, not corrupted. This is why the provider being swappable (point 14) or occasionally wrong doesn't compromise correctness - every action it can take routes through code that was already correct on its own, per CLAUDE.md point 1.
41. **`answerClarification`'s yes/no interpretation is deterministic, not model-based** (`internal/graph/resolvers.go:interpretYesNo`) - it tokenizes on the first letters-only word so punctuation doesn't break it ("yes, it does" works) but a whole-word match still rejects "yesterday"/"nothing" rather than false-positive prefix-matching them. Ambiguous input is a GraphQL error asking for a clearer answer, never a guess. Covered by `clarification_test.go`.
42. **The agent loop only runs from `worker.runInspect`, never from `runRepair`'s own recheck.** A repair's recheck either resolves the case (no action needed) or leaves it at `NEEDS_REVIEW` for something repair can't fix (color mode, malformed data) - `escalate` is the correct terminal state either way, and NOT re-invoking the agent there closes off any possibility of a repair→agent→repair loop against the same pristine original (see point 25's "repair always targets the pristine original" - repeated auto-triggers would just keep re-repairing the same source).
