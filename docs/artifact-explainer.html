01

The problem

A sticker print shop's customers upload their own artwork files. A lot of those files aren't actually print-ready, and the reasons are specific and mechanical, not vague "quality" issues:

Missing bleed

No safety margin

Full-bleed prints need art that extends past the cut line. If the file stops exactly at the edge, the die-cutter's real-world tolerance leaves a thin white sliver on the finished sticker.

Low resolution

Under 300 PPI

A file that looks fine on a phone screen can be well under the pixel density needed once it's scaled up to the requested physical size — it prints visibly soft or pixelated.

Ambiguous trim

Is this already bled?

For a "full bleed" order, the system can't tell from pixels alone whether the upload is just the trim area (needs a margin added) or already includes bleed (needs nothing) — guessing either way risks a bad print.

Today that review is a manual job: someone opens the file, eyeballs it, and either emails the customer or fixes it by hand. It doesn't scale, and it's inconsistent between reviewers. The brief was to automate the review and a narrow slice of the fixing — without ever letting a model guess at a measurement or silently ship a bad print.

02

Why "just call an LLM" doesn't cut it

The interesting engineering isn't the AI call — it's everything around it that makes the AI call safe to trust in production:

Durable

Orders sit in a real queue in Postgres. If a worker process dies mid-job, nothing is lost and nothing runs twice — a fresh worker picks up exactly where the crash left off. Verified by literally reproducing "artifact written to storage, then crashed before the database commit" and confirming a resumed worker doesn't duplicate the write.

Bounded

The model never measures anything. Every number — pixel width, PPI, bleed margin in inches — comes from deterministic Python checks. The model's only job is picking one next action from three: ask a question, request a repair, or escalate. And Go independently re-validates that choice against the real findings before acting on it — the model's stated reasoning is never trusted at face value.

Measured

"The agent resolved the order" isn't a claim you should just take on faith. This project built a real evaluation harness comparing the agent against a rules-only baseline and a hand-written deterministic script — see section 5 for what that actually showed.

The honest finding

Once the script had the same ability to escalate that the agent has, it matched the agent exactly, fixture for fixture — at zero model cost. This isn't a disappointing result to hide: having either an agent or a smart deterministic fallback closes all 8 cases rules alone leave stuck. The LLM didn't beat good deterministic engineering here — and knowing that, instead of assuming the model must be helping, is the actual point of running the comparison.

06

Go deep — L1 → L3

The one-line answer, then how it actually works, then the edge cases and tradeoffs a senior interviewer would push on. Expand L2/L3 on whichever mechanism you want to drill into.

1. Why the model never measures anything

L1

The agent gets exactly one decision — ask a question, request a repair, or escalate — chosen from findings a deterministic Python service already computed. It never touches pixels itself.

L2 How it actually works

runAgentDecision reads the specific inspection's findings via job.AgentSourceJobID — never "whatever the latest findings happen to be" for the order — builds a DecisionInput, and calls Groq with tool_choice forcing exactly one structured tool call: ask_clarification, request_repair, or escalate. Go then independently re-checks the real findings for the ONE precondition each action requires — e.g. request_repair requires hasConfirmedInsufficientBleedFinding(findings) to actually be true — before ever acting. If the model's choice doesn't match what the findings support, Go overrides it to escalate and records that the model's own choice was rejected, not silently "corrected."

L3 Deep dive — why this boundary, not a freer one

The alternative design — let the model call a "measure_bleed" tool itself, or reason freely about the image — was rejected because a hallucinated measurement is indistinguishable from a real one until a customer's print ships wrong. That failure mode is worse AND harder to catch than "the model picked the wrong of three pre-vetted actions," which Go's re-validation catches deterministically, on every single call, with zero additional model cost.

The general principle this project is built on: push AI to the smallest, most reversible, most independently-checkable decision point available, and keep everything that determines whether a physical object is correct — pixel measurements, color mode, trim geometry — in code you can unit test with fixed inputs and fixed expected outputs. That's not "restrict the model's intelligence" — it's separating what MUST be deterministic from what CAN safely be probabilistic.

2. Durable job queue & what "crash-safe" actually means here

L1

Every step is its own row in a jobs table, claimed by exactly one worker with a single atomic SQL statement, so a crash mid-job never loses or duplicates work.

L2 How it actually works

The claim is one statement: UPDATE jobs SET status='RUNNING', worker_id=$1, lease_expires_at=now()+interval WHERE id=$2 AND status='QUEUED' AND (lease_expires_at IS NULL OR lease_expires_at < now()) RETURNING *. The WHERE clause is what makes it atomic — two workers racing on the same row can't both match it, because whichever transaction commits first changes status out from under the other's WHERE condition. If a worker dies mid-job, nothing needs to detect that explicitly — the lease just expires, and the next poll (this worker or another) reclaims it.

L3 Deep dive — the real hazard isn't the claim, it's the write

Claiming the same job twice is the easy 80% of "durability" and the lease handles it trivially. The actual hazard is that storage writes (to GCS/local disk) are not transactional with the Postgres commit that marks a job complete — so a worker can write repaired image bytes to storage, then crash before the DB row that records the repair commits.

This was tested directly, not assumed: call the repair endpoint manually to get the exact bytes a real repair would produce, write them to their real content-addressed path (reproducing "storage write already succeeded"), then hand-insert a RUNNING job with an already-expired lease and no corresponding repairs/assets row (reproducing "crashed before the transaction committed"). A fresh worker reclaims the job and reprocesses it FROM SCRATCH — calls /repair again, gets the same bytes (deterministic given the same input), and its own Storage.Put call recognizes the content-addressed path already exists, so it's a safe no-op instead of a duplicate write. Net result: exactly one repairs row, no duplicated storage, case reaches RESOLVED. The honest caveat: this proves the DB/storage state a crash leaves recovers correctly — it does not prove an actual SIGKILL mid-syscall behaves identically, since a genuinely partially-written file is a different failure mode this hasn't exercised.

3. Optimistic concurrency (case_version)

L1

Every mutation that changes an order's state takes the caller's last-known caseVersion; if it's stale, the mutation fails instead of silently overwriting something newer.

L2 How it actually works

Every order carries a case_version integer, bumped on every state-changing operation. A frontend call like confirmTrim(orderId, isTrimOnly, caseVersion: 3) compiles to SQL with WHERE id=$1 AND case_version=$2 — if the background worker already moved the case to version 4 in the meantime, the update matches zero rows and the API returns a clear conflict error instead of silently applying a stale decision on top of newer state.

L3 Deep dive — why this race is real here, specifically

This matters because there are genuinely TWO concurrent writers to the same order: the human via the frontend, and the worker acting asynchronously in the background on its own schedule. A "last write wins" design would let a customer's stale-page click undo something the agent already decided a second earlier — e.g. re-submitting a trim answer after the case already auto-escalated for an unrelated reason — corrupting the state machine silently, with no error and no trace.

The tradeoff against pessimistic locking (row-level locks held across the whole interaction) is that optimistic concurrency never makes one writer block waiting on the other — it just turns a genuine conflict into a visible, retryable error on the rare occasion one actually happens. That's the right tradeoff here specifically because conflicts are infrequent (one human, one background process) but silent corruption would be much worse than an occasional "please reload and retry."

4. The evaluation methodology

L1

34 fixtures, run three ways — rules only, the real agent, and a deterministic script given the same escalation power — because "the agent resolved 18/34" means nothing without a fair baseline.

L2 How it actually works

The naive comparison (agent vs. rules-only) made the agent look artificially strong, because rules-only had no way to escalate a case it couldn't resolve — it just left 8/34 cases silently BLOCKED forever. That's a test of "does having any decision-maker help," not "does the AI specifically help." So a matching escalation capability was added to a hand-written deterministic script (evals/scripts/run_eval.py's escalate_case), so both arms could reach a real terminal state on every fixture — turning it into an apples-to-apples comparison.

L3 Deep dive — a bug in the eval harness itself

Two more corrections came out of taking the measurement seriously. First, "passed" (correct final state, escalation included) and "resolved" (order actually reached RESOLVED) are reported as separate numbers on purpose — conflating them overstates what a high pass rate means, since a correctly-escalated case passes without ever resolving.

Second, and more interesting: a failed Groq API call used to get recorded with the exact same escalate outcome as the model genuinely choosing to escalate — meaning a broken API key silently looked like consistent, defensible model behavior across five separate deployment-verification runs, until server logs were read directly. The fix distinguishes provider error (<category>) → escalated for review from model chose to escalate at the persistence layer, and the harness gained a no_provider_error check that fails a fixture outright if it hit a real API error — because a fixture that never actually reached the model is not evidence about the model, no matter what its final state looks like.

5. The security boundary: IAM, not network isolation

L1

The image-processing service is "private" because every caller needs a signed identity token, not because of which network can reach it — and the public demo blocks all writes server-side, not just in the UI.

L2 How it actually works

graph.Resolver.guarded() wraps all 7 GraphQL mutations in one place; when Resolver.ReadOnly is true (set via READ_ONLY_DEMO on the deployed instance), every mutation returns the same clear error before any of its own logic runs — reads stay open. Separately, every call from the API/worker to the image service attaches a Google-signed identity token fetched from the Cloud Run metadata server, its audience scoped to that exact service's URL, and roles/run.invoker is granted only to the one service account that needs it — never allUsers.

L3 Deep dive — the ingress:internal trap

ingress: internal was tried first, and reverted. Cloud Run only treats a caller as "internal" if it's attached to a Serverless VPC connector or uses Direct VPC egress — without one, a sibling Cloud Run service's own outbound call still leaves over the public internet, and gets rejected by the front-end load balancer identically to an outside caller. This was confirmed, not assumed: curling the "internal" service directly from outside returned the exact same 404 route-not-found page the worker's own failed calls were logging.

Switching to ingress: all + IAM-only auth was the actual fix — it moves the security boundary from "which network can reach you" to "who holds a valid signed token," which is the more defensible boundary anyway for a service that will always be reached over some network. The tradeoff made explicit rather than hidden: this needed a real code change (fetching an identity token in pyclient.go, gated on K_SERVICE so local docker-compose — no metadata server, no auth — is unaffected), not just a config flip.

07

Reliability, found by actually deploying it

Two of the most useful bugs in this whole project only showed up after it went live on Cloud Run, never in local testing — both are covered in full technical depth in section 6:

A silent failure that looked like a real decision

A trailing newline in the LLM API key made every provider call fail — and looked identical to a genuine model escalation for five separate test runs, until server logs were read directly. See deep-dive #4.

Read-only by default in public

No user-account system exists yet, so every mutation is rejected server-side on the live deployment, not just hidden in the UI. See deep-dive #5.

08

Honest limits

Stated plainly, the way the rest of this project tries to be:

  • Mitigated No user authentication or order ownership yet — the public demo runs read-only server-side rather than leaving this open.
  • Open The worker is a long-running poll loop, not a true Cloud Run Job — correct as deployed, but not the more idiomatic serverless shape.
  • Open Crash recovery is verified against a hand-reproduced crash state, not an actual killed process.
  • Clarified The LLM provider is Groq, an inference host for open-weight models — unrelated to xAI's Grok, and never described as such anywhere in this project.
